# API Design

Base URL (local dev): `http://localhost:8000`
Interactive OpenAPI docs: `http://localhost:8000/docs` (auto-generated by FastAPI from `api/main.py` + `api/schemas.py`)

All responses are JSON. All monetary fields are INR. All score fields are on
a 0–100 scale unless stated otherwise.

## Auth (production note)

The prototype ships with no auth (`allow_origins=["*"]` CORS, no API key)
for ease of local demo. A production deployment would add an API-key or
OAuth2-client-credentials layer per lender/LSP tenant, since every endpoint
here handles sensitive financial data.

---

## 1. Data ingestion

### `POST /api/v1/msme/ingest`

Stores a raw, consent-aggregated MSME record for later scoring. Does not
compute a score (see `/api/v1/score` to do both in one call).

**Request body:** `MSMERawInput` (see `api/schemas.py`) — 27 raw
alternative-data fields (business profile, GST, UPI, banking, payroll,
invoices/vendors, growth/seasonality) plus optional `msme_id`.

**Response:**
```json
{
  "msme_id": "MSME-NEW-000001",
  "status": "ingested",
  "message": "Record stored; call /api/v1/score to generate the Financial Health Card."
}
```

### `GET /api/v1/msme/search?q=<substring>&limit=25`

Search/browse known MSME_IDs (seed dataset + any ingested at runtime).

**Response:**
```json
{"count": 9, "results": ["MSME0000001", "MSME0000002", "..."]}
```

---

## 2. Score generation

### `POST /api/v1/score?explain=true`

Ingests (if new) and scores a raw MSME record in one call — the primary
entry point for a new NTC/NTB business with no prior `msme_id`.

**Request body:** `MSMERawInput`
**Response:** `HealthCardResponse` (see §4 below for the shape)

---

## 3. Credit recommendation

### `GET /api/v1/credit-recommendation/{msme_id}`

Lightweight endpoint for a loan-origination system that only needs the
credit decision, not the full explainability payload.

**Response:**
```json
{
  "msme_id": "MSME0000002",
  "credit_eligible": "No",
  "credit_risk_category": "High",
  "probability_of_default": 0.1975,
  "recommended_credit_limit_inr": 0.0
}
```

---

## 4. Health Card retrieval

### `GET /api/v1/health-card/{msme_id}?explain=true`

Full Financial Health Card for a known MSME (seed dataset or previously
ingested). Recomputed from stored raw data on every call (cheap — tree
model inference, not retraining), so it always reflects the latest models.

## 5. Explainability

### `GET /api/v1/explain/{msme_id}`

Returns just the `explainability` block above — SHAP top-driver
attributions for the overall score, risk category, and eligibility
decision — for a UI that wants to render "why this score" independent of
the rest of the card.

---

## 6. Dashboard integration

### `GET /api/v1/dashboard/{msme_id}`

Aggregated payload the Streamlit dashboard (or any other frontend) needs in
a single round trip: the full health card plus simulated 12-month trend
series (GST sales/purchases, UPI inflow/outflow, bank credits/debits,
payroll) for charting.

**Response:**
```json
{
  "health_card": { "...": "HealthCardResponse, see above" },
  "trends": {
    "months": ["M-11", "...", "M-0"],
    "gst_sales": [1056244.17, "..."],
    "gst_purchases": ["..."],
    "upi_inflow": ["..."], "upi_outflow": ["..."],
    "bank_credits": ["..."], "bank_debits": ["..."],
    "payroll": ["..."]
  },
  "generated_on": "2026-09-27"
}
```

> **Note:** the source dataset is one cross-sectional snapshot per MSME
> (no monthly history), so `trends` is deterministically reconstructed from
> each MSME's growth rate + seasonality index (`src/trends.py`) rather than
> real historical statements. A production deployment plugs actual monthly
> GST/UPI/bank statement series from the Account Aggregator feed into the
> same `trends` shape.

## Error handling

- `404` — unknown `msme_id` (not in the seed dataset and never ingested).
- `422` — request body fails `MSMERawInput` validation (FastAPI/Pydantic's
  standard validation-error shape).
- `500` — unexpected scoring failure (should not happen in normal operation;
  logged server-side).
